# Registro público de resultados — Fase 1

O domínio público `nexoresearch.org` é construído pelo workflow de Pages a partir de `nexo-atlas/`; `nexo-one/` é um runtime Vercel separado. Nesta revisão, o Cockpit privado de `nexo-one` também recebeu esclarecimentos sobre cobertura da SHADOW e ajustes de legibilidade, sem mudar autenticação, flags ou aprovações legadas. A Tower continua a autoridade operacional. Este registro é uma projeção editorial do catálogo público, sem leitura de Tower nem nova autoridade científica.

`src/atlas/researchRegistry.json` cobre as 19 perguntas do artefato versionado `worker/public-cosmology.json`. Existem 169 textos de referência. As versões científicas, estado editorial científico, identidade canônica, DOIs de dados/código, incertezas estruturadas e histórico não estão disponíveis no artefato. Os vetores `versions` permanecem vazios e a interface exibe explicitamente a informação ausente. A seleção live pode incluir perguntas não presentes nesse arquivo: elas recebem a mesma ficha de dados ausentes, sem gravação ou identificação inventada.

`/claims/` mostra somente o cruzamento da seleção pública corrente com os textos cujo conteúdo, nos quatro campos, corresponde exatamente ao índice SHA-256 derivado do artefato `public-cosmology.json` na revisão pública indicada no próprio índice. O hash identifica texto, não teste físico nem entidade científica. A classificação de evidência vem da última revisão que referencia aquela linha exata, quando disponível; não é herdada de outra análise agrupada na mesma pergunta. Uma revisão retratada retira aquela linha das alegações atuais, preservando o histórico. A classificação ausente permanece explícita e nunca é inferida do estado de publicação do site. Sem seleção disponível, a lista de alegações não mostra o cache anterior. Atualizações selecionadas sem correspondência ao artefato continuam no catálogo existente, mas ficam fora desta lista até uma fonte versionada ser revisada.

O esquema em `src/contracts/research-registry.mjs` permite histórico com fontes públicas por campo e exige motivo para alterações após a primeira versão da mesma análise. Cada versão liberável exige `analysisId` científico explicitamente comprovado e uma única `sourceKey` canônica de alegação. Cada campo preenchido, inclusive identidade, versão e motivo, precisa de uma referência `provenance` contendo caminho no repositório, commit imutável, SHA-256 dos bytes e ponteiro JSON. O verificador confere o valor e a associação ao registro da pergunta no artefato público fixado. `result` aponta ao resultado publicado daquela linha; metadados científicos apontam a campos explicitamente estruturados em `research`, sem usar o estado da seleção do site. O verificador não abre URLs nem arquivos arbitrários indicados pelo registro. `status: published` exige DOI ou arXiv de publicação com a mesma proveniência; DOI de dados ou software não substitui essa identificação.

A resolução das alegações descobre a identidade científica pela linha referenciada e consulta a última versão dessa identidade, mesmo que o texto tenha mudado. Uma seleção que ainda contenha o texto antigo não o apresenta como alegação atual depois de uma correção ou retratação. Textos iguais atribuídos a identidades científicas distintas são ambíguos: o build rejeita essa associação e a interface não escolhe uma identidade por aproximação.

O contrato não proíbe versões preenchidas: os testes de software demonstram duas versões e motivo usando exclusivamente fontes sintéticas. Um teste com repositório Git temporário real preserva v1 no commit A quando v2 corrige apenas incerteza no commit B, mantendo os quatro textos editoriais iguais. O índice conserva listas de linhas por hash e ponteiros originais, evitando sobrescrita de linhas distintas com texto igual. O artefato real atual não contém os campos estruturados necessários; por isso seus registros continuam vazios. A interface conserva versões anteriores, mostra os valores ausentes como não informados e apresenta links e hashes de origem nos detalhes.

`researchSourceCatalog.json` fixa as origens históricas por commit, caminho e SHA-256, sem remover as necessárias a versões anteriores. No momento só autoriza o artefato público `nexo-atlas/worker/public-cosmology.json`. Para registros preenchidos, o build lê os blobs diretamente pelo Git, verifica os hashes e exige que cada commit seja ancestral da base pública revisada: `NEXO_PUBLIC_BASE_COMMIT` na CI ou `origin/main` localmente. Não aceita uma origem apenas adicionada na própria branch. Uma nova origem científica precisa já estar pública, versionada e revisada antes de entrar nesse catálogo; caminhos privados e URLs arbitrárias são rejeitados. A leitura limita o catálogo a 100 origens e cada blob a 5 MB.

A comparação automatizada de PR contra o commit-base impede modificar ou apagar versões anteriores. A CI, com histórico completo, confronta os bytes com o blob do commit declarado. Em checkout raso ou arquivo sem Git, somente o catálogo sem versões pode usar a comparação com o blob fixado, com aviso de vínculo commit→blob não verificado; versões preenchidas exigem confirmar os bytes no commit. Preservação de histórico científico real continua pendente de fonte aprovada. Não copie registros privados para preencher lacunas.

`npm run check` valida o contrato durante o build e executa os testes; `node scripts/build-pages-public.mjs` materializa as páginas estáticas. O workflow de pull request `.github/workflows/nexo-atlas-pr-ci.yml` executa os checks e axe-core local em Chromium, sem deploy. Uma análise automatizada não prova conformidade WCAG completa. O roteiro continua a exigir avaliação manual de leitor de tela e dispositivos físicos.
