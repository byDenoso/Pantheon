# NEXO ONE

Personal cockpit in `Pantheon/nexo-one`. React 19, TypeScript, Vite, Node 24. No database. Existing Atlas is unchanged.

## Current scope

Five views (NOW, LOOPS, DAY, CONTEXT, RECALL), dark/light responsive shell, command parser, modal focus panel, provenance validation, seven isolated read adapters, bounded parallel compilation, incremental NDJSON delivery, last-valid warm-instance cache, semantic world diff, explicit source coverage and single-user signed session cookies.

`PERSONAL_LOOP_V1` is implemented in the existing NEXO ONE runtime. It adds the private `GET /api/personal` snapshot plus the governed `POST /api/personal/action` loop. L3 canonical Task/Commitment upserts may execute automatically through the capability fabric with verified NEXO readback; L4 Gmail draft and Calendar event creation require approval bound to the exact server proposal fingerprint; send-mail, Drive mutation and unregistered V1 operations remain denied at L5. Public SystemState and Atlas/research surfaces keep their sanitized anonymous boundary.

Private usefulness is configuration-dependent. A deployment without the private session and Google/NEXO credentials must report that state honestly and must not fake private provider availability. The ChatGPT connectors are not application credentials. No private user records or test fixtures are bundled or exposed publicly. See `docs/PERSONAL_LOOP_V1.md` for the runtime contract and acceptance checks.

## Run

```sh
cd nexo-one
npm ci
npm run check
npm run dev
```

Node 24 is required (native type stripping for pure TypeScript model tests). Local dev binds to 127.0.0.1:4173. `npm run preview` serves the production build. If your remote browser cannot access localhost, use a verified deployment for visual interaction.

Server tests use synthetic fixtures only in `test/`; UI production never substitutes them for an unavailable provider. Browser CI installs pinned Playwright in an isolated tool directory; `PLAYWRIGHT_MODULE` can select that installation. Its route fixtures do not enter the deployed app.

## Configure private access

See `.env.example` for **names only**. Provision these directly in the existing `nexo-one` Vercel project; never in chat, source files or client-prefixed variables.

1. Set `NEXO_SESSION_SECRET` (at least 32 random characters) and `NEXO_PASSWORD_HASH` (scrypt format generated by `scripts/password.mjs` reading stdin). Protect `/api/session` with a platform rate limit as well; the implemented rate bound is per warm instance. Password login is an initial single-user gate, not a complete identity-management service.
2. Google authorization should use the bounded PERSONAL_LOOP_V1 scopes documented in `docs/PERSONAL_LOOP_V1.md`. Reads require Drive/Gmail/Calendar/Sheets read access; mutation scopes are requested separately for Gmail draft, Calendar event and canonical NEXO Sheet writes. Token exchanges remain server-side. The ChatGPT connectors are not application credentials.
3. GitHub: defaults to the public `byDenoso/Pantheon` repository without a token. Private mode can use a fine-grained read token. Open issues/PRs are bounded to 100; the UI reports partial coverage. RECALL searches issue/PR content and repo metadata; it does not yet search every code file.
4. Vercel: set a read credential, team ID and the exact project ID. This remains an observation adapter; deployment control is not exposed as a personal action.
5. NEXO: configure the canonical NEXO source/Sheet according to `.env.example` and `docs/PERSONAL_LOOP_V1.md`. Do not create or designate a new truth owner to satisfy this input. Dates, statuses and origin links are validated. No heuristic rewriting of canonical registers.
6. Atlas: `ATLAS_GRAPH_URL` is the existing authorized Graph Contract V1 URL. Add `ATLAS_SOURCE_TOKEN` only if that API expects a bearer credential. Private graph reads require a valid NEXO ONE session. No Neon connection is added.

After configuring providers, redeploy to staging and verify authenticated live reads, governed mutations and unauthenticated non-disclosure. Review credential scope and viewer access before releasing any private integration.

## API

`GET /api/world` compiles all available providers. `?stream=1` emits one WorldState per completed provider, allowing the shell to render fast sources first. `?refresh=1` bypasses the short cache; concurrent snapshots are coalesced. Every reader has an 8-second outer deadline even if it ignores AbortSignal.

`GET /api/health`, `/api/now`, `/api/loops`, `/api/day`, `/api/context?id=NEXO`, `/api/recall?q=...` are projections. Calendar fetches a rolling two-week window; choosing a day outside it does not imply that day is free. Query strings contain search text, not credentials. API responses use `private, no-store` and `Vary: Cookie`.

`GET/POST/DELETE /api/session` reads/creates/clears the signed HttpOnly session cookie. Private reads are gated **before** adapter invocation. Public mode never passes a private token to GitHub and never serves a private cache entry. Authentication loss discards the affected private provider cache.

`GET /api/personal` requires a private session and returns the personal provider state, canonical personal model, proposals, follow-ups and semantic fingerprint. `POST /api/personal/action` requires a private session plus same-origin request and passes the proposal through the existing L0-L5 policy and capability fabric. L3 canonical writes require provider/canonical readback before completion. L4 external mutations require approval for the exact proposal fingerprint. Unsupported writes fail closed. Full details live in `docs/PERSONAL_LOOP_V1.md`.

## Semantics and limits

- NOW uses explicit due dates, assignment, priorities and blocked state. Unread messages do not create commitments. Closed events do not become overdue tasks. Cached/stale items cannot assert live urgency.
- Provider count is `null` on unavailable reads, `0` only after a valid empty result. Successful bounded reads carry `partial` when more pages exist.
- World fingerprints exclude polling timestamps, preserve content/source revisions, include freshness and availability, and are stable under provider/item order. Diffs compare completed reads; removal from the view is not asserted as deletion at the owner.
- NEXO observations are not re-dated on read; Atlas FALLBACK/STALE is carried through. Context inference from names is derived navigation, not a scientific claim.
- Last-valid cache is **ephemeral server memory** and the active browser session; it is not cross-device persistence or a new canonical store. Only UI theme/tab are stored locally. On reload/cold start, sources must be fetched again. Auto-refresh runs every 5 minutes while visible and on returning to a stale tab; there is no background automation inside the web app.
- DAY displays fixed events, overlap indicators and unassigned flexible work. Duration-aware allocation and recovery-margin calculation remain outside V1.
- PERSONAL_LOOP_V1 supports canonical Task/Commitment persistence, Gmail draft creation and Calendar event creation only through their registered policy/capability paths. Gmail sending, Drive mutation and unregistered provider actions remain denied.
- Initial browser screenshots require baseline review before visual regression can claim an approved baseline. The CI generates screenshot evidence, not a fabricated visual approval.

## Deployment and rollback

The only project is `nexo-one` (`prj_rFoAEgGt4gFNr8DHEOzxY7keS16W`). `scripts/package-release.mjs` packages the exact built assets and dependency-free server, with a SHA-256 file manifest. It excludes fixtures, secrets and node_modules.

`.github/workflows/nexo-one-ci.yml` runs types, unit/adapter/security tests, desktop/mobile browser scenarios and packages immutable release artifacts. Deployment workflows are manual, scoped to the same project, and require dedicated secrets and environment approval. Production uses a staged production build before `vercel promote` so there is no rebuild between staging verification and promotion. See `docs/RELEASE.md`.

A green build or a Git integration deployment is not by itself proof that private PERSONAL_LOOP_V1 is operational. Promotion acceptance requires the checks in `docs/PERSONAL_LOOP_V1.md`, including unauthenticated denial, authenticated private reads, governed L3/L4 behavior and verified provider/canonical readback. Missing credentials must remain a visible degraded/configuration state rather than being treated as success.

Sources used for the integration design: [Google server-side OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [GitHub Issues REST](https://docs.github.com/en/rest/issues/issues), [Vercel deployment creation](https://vercel.com/docs/rest-api/deployments/create-a-new-deployment), [Vercel staged production promotion](https://vercel.com/docs/deployments/promoting-a-deployment).
